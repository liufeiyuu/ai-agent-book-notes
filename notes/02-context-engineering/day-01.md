## 闭卷热身与反馈

### 1. 为什么上下文不等于对话历史？

原始回答：

> 因为上下文的概念要大于对话历史，对话历史只是上下文的一部分，上下文还包括系统提示词、工具列表、用户输入、工具调用结果。

反馈：主方向正确，但还缺少另一个方向。上下文可以包含不属于对话历史的系统规则、工具定义、用户记忆、知识库证据和任务状态；反过来，完整对话历史也不一定全部进入本轮上下文，旧消息可能被删除、摘要或按需检索。因此不能简单理解为“上下文永远是对话历史的超集”。

### 2. 工具执行后的第二次模型请求包含什么？

原始回答：

> 这个请求里要包含系统提示词、用户输入、工具调用结果、工具列表。因为大模型本身是没有记忆的，所以它每次的对话都需要给它之前对话的信息。

反馈：无状态判断正确，但漏掉了关键的 `assistant` Tool Call。第二次请求至少需要：System Prompt、用户消息、模型第一次返回的 `assistant.tool_calls`、带对应 `tool_call_id` 的 Tool Result，以及仍可使用的工具定义。Tool Call 与 Tool Result 必须成对保留，模型才能知道结果对应哪个调用以及自己为什么得到这个结果。

### 3. 哪些信息可以删除、压缩或必须原样保留？

原始回答：

> 可以删除的是最近三轮闲聊，已经使用完的五万字搜索结果，已失败方案及失败原因。可以压缩 System Prompt 中的安全规则、早期用户约束，必须原样保留的是工具返回的订单号，当前任务 To Do。

反馈：这里存在本次前测最重要的风险。

- System Prompt 中的安全规则应作为稳定前缀原样保留，不能交给自由文本摘要改写。
- “不要访问外网”是硬约束，应原样保留或写入受控的结构化约束字段。
- 已失败方案及失败原因通常不能直接删除，否则 Agent 可能重复失败；应压缩成“尝试了什么、为何失败、不得如何重试”。
- 订单号等精确标识符应结构化、原样保留。
- TODO 应作为结构化任务状态维护，而不是只留在自然语言历史里。
- 大体积搜索结果可移出运行时上下文，但要先保留相关事实、来源和引用；原文可归档在外部存储。
- 与任务无关的闲聊可优先从运行时上下文移除。

需要区分两个动作：从本轮模型上下文移除，不等于从日志、磁盘或审计记录中永久删除。

### 5. 如何证明压缩有效？

原始回答：

> 我觉得不一定能证明压缩有效，因为可能压缩失败了。检查哪些证据我不知道。

反馈：“程序输出了答案”不等于压缩有效。至少要检查关键约束是否保留、精确事实是否未失真、模型是否避免重复失败、最终行动是否与完整上下文一致、引用是否仍可回溯，以及 Token、延迟和成本是否确实下降。

## 当前认知诊断

已经掌握：

- 上下文包含的信息多于普通聊天消息。
- 模型 API 本身无状态，每轮需要重新构造输入。
- 大体积、低价值内容需要从运行时上下文中移除。

本节需要重点修正：

- 上下文与完整历史不是简单的包含关系。
- Tool Call 与 Tool Result 是必须配对的协议事件。
- 信息的“运行时移除”“有损压缩”“结构化提炼”和“永久删除”是四种不同操作。
- 压缩必须用可观察证据评测，不能只看是否生成了答案。

### 1. 上下文为什么不只是对话历史？

原始回答：

> 上下文是对话历史的超级，上下文包括 messages 和 tool definitions。Messages 里面包括 system prompt，然后还有 trajectory，动态轨迹，动态轨迹又包括 user input，assistant message，以及 tool result。然后其中对话历史只是 assistant message。

反馈：已经正确识别出 API 层的 `messages` 和 `tools`，也识别出了 System Prompt 与动态轨迹，但有两处需要修正。

第一，对话历史不是只有 Assistant Message，而是多轮交互中的 User Message、Assistant Message/Tool Call 和 Tool Result 序列。第二，上下文不是“完整对话历史的超集”：它可以加入系统规则、记忆、知识库和状态，也可以删除、摘要或按需检索部分旧历史。更准确地说，上下文是 Harness 为本轮模型调用构造的运行时工作集。

### 2. 为什么必须带回 Assistant Tool Call 和 Tool Result？

原始回答：

> 因为这样才能把工具调用的结果和模型的 token 对应起来。这样模型才能知道什么结果对应着哪个工具调用。是通过 tool Call ID 对应起来的。

反馈：`tool_call_id` 不是把结果和模型的某个 token 对应起来，而是把一条 Tool Result 与先前的一次结构化 Tool Call 事件关联起来。并行调用多个工具时，这个关联尤其重要。保留 Assistant Tool Call 还能让模型看到自己为什么请求该工具、使用了哪些参数，并维持完整的因果轨迹。

### 3. Model、Harness、Environment 分别负责什么？

原始回答：

> Model 负责决策和处理 Harness 给他的信息，Harness 负责对 Model 输出的决策去进行对环境的输入，或者读或者写，去操作，去改变这个环境，Environment 就是环境本身，它就是存在在那里，然后等着 Harness 跟它进行交互。

反馈：主干正确。进一步精确化：Model 根据上下文提出行动或最终回答，但不执行工具；Harness 构造上下文、调用模型、校验工具名和参数、执行权限策略、调度工具、记录结果并控制循环；Environment 是被观察或产生真实状态变化的外部世界。读操作只产生观察，写操作才可能改变环境。Context 是 Environment 观察结果在 Agent 内部的表示，不是 Environment 本身。

## 阅读后的关键修正

```text
完整对话历史
= User Message + Assistant Message/Tool Call + Tool Result 的历史序列

本轮上下文
= 从历史和其他信息源中选择、组织出的运行时工作集

tool_call_id
= Tool Result 与 Tool Call 事件之间的关联标识
≠ Tool Result 与某个模型 token 的关联
```

## 两分钟确认题

### 1. “上下文是完整对话历史的超集”是对还是错？

原始回答：

> 这句话是错的，因为完整的对话历史它可能有多轮，然后它不只是模型的返回，它还有历史用户的输入，历史工具调用的结果，等等。它还可能有用户的 memory 记忆，然后知识库等等信息。

反馈：判断正确，也修正了“对话历史只有 Assistant Message”的错误，但仍需注意：用户记忆库和知识库本身不是对话历史。完整对话历史由 User、Assistant/Tool Call、Tool Result 等交互事件组成；记忆和知识库是独立信息源。只有其中某些内容被检索并注入某轮请求后，那份被注入的副本才进入本轮上下文。上下文既可能只选取部分历史，又可能加入历史之外的信息，因此两者不是固定的超集关系。

### 2. 两个并行工具结果如何进入第二次请求？

原始回答：

> Harness 会在一个循环中去调用这两个工具，然后依次把工具调用的结果 push 到 messages 里面，会输入给模型。然后这个工具调用结果中的 ID，它有一个 tool_call ID，这个 tool_call ID 就是模型之前返回的 tool_call 里面的这个 ID。

反馈：ID 配对理解正确。若两个工具没有数据依赖，Harness 可以并行执行，不必串行等待；收集结果后，把两条 Tool Result 放在同一条 Assistant Tool Call 之后。第二次请求的核心顺序如下：

```text
System Message
User Message
Assistant Message
  ├── Tool Call: call_weather
  └── Tool Call: call_time
Tool Result: tool_call_id = call_weather
Tool Result: tool_call_id = call_time
```

`tools` 定义仍作为请求顶层字段提供（如果模型仍被允许继续调用工具）。结果消息的先后顺序不是主要关联依据，`tool_call_id` 才是。
