# Agent 如何调用大模型：理解 API 的上下文结构

## 消息的四种角色

大模型 API 的核心是一个消息列表（messages），列表中的每条消息都有一个角色（role）标识，模型根据角色来理解每条消息的含义和来源：

1. system：系统提示词。开发者编写，定义 Agent 的身份、行为规则、约束条件。模型将其视为最高优先级的指令。整个对话过程中通常只有一条，放在消息列表最前面。
2. user：用户消息，来自终端用户的输入，是 Agent 要响应的请求。
3. assistant：助手消息。模型之前的回复，包括文本回复和工具调用请求。
4. tool：工具结果。Agent 执行工具调用后，将调用结果以 tool 的消息返回给模型。每条 tool 消息通过 tool_call_id 与对应的工具调用请求关联。

除了这四个，工具定义 tools，也作为请求顶层字段传入，它不是消息角色，它告诉模型有哪些工具可以用，每个工具的参数是什么。

本阶段最小调用模型按无状态请求理解：Harness 为每轮提供必要上下文，并按协议传入工具定义等信息。完整历史不必全部重发，可以筛选、压缩和按需检索。


## 带工具调用的多轮交互：Agent的核心循环

这里有三个关键细节：
1. 第二次请求需提供继续任务所需的历史与状态，不能假定模型自动记住上次调用；不要求无条件保留完整历史
2. 第一次的 assistant 消息被原样放回消息列表，让模型能看到自己之前做了什么决策
3. tool 消息通过 tool_call_id 与对应的工具调用关联，模型根据此知道哪个结果对应哪个调用

# KV Cache 友好的上下文设计

KV Cache 保存历史 token 的 Key/Value 中间结果，避免在后续生成时重复计算这些状态。跨请求能否复用前缀，还取决于服务是否支持以及缓存是否命中；新增 token 仍需计算。

稳定前缀有利于缓存复用，动态信息尽量后置。规则发生真实变化时可以更新系统提示词；“尽量稳定”不等于“永远不能改”。


使用接口规定的结构化消息与工具协议，保留角色、调用 ID 和工具结果的关联。Chat Template 负责把消息结构转换为模型输入；普通字符串拼接不能自动保留这些协议语义。
