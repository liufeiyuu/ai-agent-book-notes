## 本轮重点

工具接口要让模型知道何时调用、怎样传参、怎样理解结果。阅读[原书第 4 章](https://bojieli.github.io/ai-agent-book/book/chapter4/)的“工具描述的艺术”即可进入本轮练习，其余内容按计划后续展开。

在当前仓库里，一次调用经过以下路径。这是依据源码整理的流程，不是本轮已经运行的 Trace：

```text
工具说明与参数 Schema 交给模型
  → 模型输出工具名和参数
  → 执行器按名称找到工具
  → parseArguments 检查输入
  → execute 执行实际操作
  → 执行器包装 ToolResult，供后续模型请求使用
```

| 位置 | 本轮看什么 |
| --- | --- |
| [calculator.ts](../../experiments/minimal-agent-ts/src/tools/calculator.ts) | `name`、`description`、`inputSchema` 描述接口；`parseArguments` 校验收到的值；`execute` 做实际运算 |
| [tool-registry.ts](../../experiments/minimal-agent-ts/src/tool-registry.ts) | `definitions()` 只提取名称、说明、参数 Schema，不将校验与执行函数自动发送给模型 |
| [tool-executor.ts](../../experiments/minimal-agent-ts/src/tool-executor.ts) | 先校验、后执行，统一包装正常结果或错误 |

这里的 `inputSchema` 是结构声明；运行时实际调用的是手写的 `parseArguments`。不能仅凭 Schema 存在，就认定本地已自动验证了其中的全部约束。

例如，将“计算 18 ÷ 3”表达成参数，可以写为：

```json
{"operation":"divide","left":18,"right":3}
```

这段 JSON 只表达请求做什么。执行结果需要由程序运行后取得，不能把参数文本当作已经完成计算的证据。

## 操作范围：字符串路径也可能不允许读取

对照[读文件工具](../../experiments/minimal-agent-ts/src/tools/read-file.ts)：`inputSchema` 声明 `path` 为字符串，但真实操作还受程序配置的目录范围约束。

- `{ "path": 123 }`：值不是字符串，在 `parseArguments` 的类型检查中被拒绝。
- `{ "path": "../outside.txt" }`：值虽然是字符串，却包含父目录跳转，在 `parseArguments` 的范围检查中被拒绝。
- `execute` 还会用 `realpath` 取得最终目标，再检查它是否位于配置目录中，防止表面合法的路径通过符号链接指向目录外。本轮只认识这个作用，不展开文件系统细节。

以上是源码对照，未新增读文件运行案例。在此实现中，前两种拒绝都会被执行器包装为 `invalid_arguments`；最终真实路径越界在执行阶段被包装为 `execution_error`。错误码表示代码在哪里失败，不能只凭错误码判断是否涉及权限或操作范围。

`rootDirectory` 由程序创建工具时配置；模型提交的是相对路径 `path`。允许读取的范围由本地程序约束，不能仅依赖工具描述中的文字要求。

### create_draft 初稿与本轮说明（2026-09-14）

学习者已说明用途是把正文保存在实验内存中、成功返回草稿 ID；尚不确定正文参数是否应叫 `path`、是否为字符串；提出空字符串和全空格使用 `trim`，并以“原文件太长”作为失败例子。

这里需要先把场景说明具体：`create_draft` 是本实验准备设计的工具，参数名由我们约定，并没有需要学习者猜出的既定答案。`path` 表示文件位置；本工具直接接收文字内容，不读取原文件。正文参数采用 `content`，类型为 TypeScript 的 `string`。

```json

```

助手协助明确的最小规格如下；最初说明时尚未实现，现已按文末记录由助手完成，不记为学习者独立完成的规格：

| 项目 | 本次实现约定 |
| --- | --- |
| 输入 | 必填 `content`，值必须是字符串 |
| 有效正文 | `content.trim()` 之后不能是空字符串；空字符串、全空格均拒绝，不创建草稿 |
| 保存内容 | `trim` 只用于判空；有效正文原样保存，包括原有前后空白 |
| 实际效果 | 向实验进程内的草稿集合添加一条记录 |
| 成功返回 | 工具返回 `{ draftId: "…" }`，ID 由程序生成；外层执行器负责包装 ToolResult |

## 接口取舍与工具粒度（2026-09-14）

本轮复用已有实际结果，只做带学讲解，没有新增实现、运行或模型调用；以下通用执行器、Skill 和自动修正文案均为对照设计，未实现。

1. **参数保真性**：草稿可能包含排版或代码缩进；保存工具只用 trim 判空，有效正文保持原样。若约定工具负责清理或改写，则应明确转换规则并反馈转换后的内容。具体例子见下文[弯引号为什么会导致替换失败](#参数保真弯引号为什么会导致替换失败)。
2. **工具粒度**：专用 create_draft 由程序固定保存规则，模型只传 content；通用 run_code 则让模型组织具体操作，更灵活，也需要更广的执行范围控制和结果检查。这里的 run_code 是假设的模型可调用代码工具，与仓库内部负责分发和包装结果的 tool-executor.ts 不是同一概念。固定业务动作适合专用工具；变化较多的代码处理可用受约束的通用执行能力。
3. **Skill 的位置**：可复用的任务指南可以指导先整理正文、再调用 create_draft 等步骤；指南本身不自动获得写入能力，实际动作仍依赖工具及其运行环境的约束。这里只认识职责，不实现 Skill。
4. **返回信息量**：当前保存工具原样写入，draftId 足以供后续引用；本地测试另行核对 Map 内实际正文，不能仅凭 ID 证明内容正确。如果工具会改写正文，最终 content 或修改摘要会帮助后续核对。返回内容应服务下一步判断，而不是一律返回最少或最多字段。

## 参数保真：弯引号为什么会导致替换失败

2026-09-15，根据学习者提供的原文截图，用具体例子重新解释。学习者已表示理解。本节说明截图描述的故障机制，未独立核实其中提到的 Cursor 历史版本，也未新增运行实验。

**核心问题：模型明明传对了文字，但文字在送到工具的途中被改了，导致工具执行失败。**

### 先看正常的替换过程

假设文件里有这一句：

```text
他说：“你好”
```

我们希望改成：

```text
他说：“再见”
```

替换工具接收两个参数：

- `old_string`：要在文件中找到的原文。
- `new_string`：找到以后，用什么文字替换它。

模型应该提交以下两个字符串的内容（这里用文本展示，避免与 JSON 外层引号混淆）：

```text
old_string = 他说：“你好”
new_string = 他说：“再见”
```

工具找到与 old_string 完全相同的原文，再用 new_string 替换，就完成了。

### 问题发生在参数传递途中

截图描述的中间传递层，会偷偷把弯引号换成直引号：

| 位置 | 实际文字 |
| --- | --- |
| 文件里的原文 | `他说：“你好”` |
| 模型传出的 old_string | `他说：“你好”` |
| 中间层修改后，工具实际收到的 old_string | `他说："你好"` |

看清这两种引号：

```text
弯引号： “ ”
直引号： " "
```

**它们是不同字符，不是同一种引号的不同显示样式。** 原文中的 `\u201c`、`\u201d` 分别表示左、右弯双引号。在 JSON 中，将弯引号编码成对应的 Unicode 转义再正确解码，不会改变字符；这里的故障是把它替换成了另一个字符。

于是，工具实际做的是：

> 在包含 `他说：“你好”` 的文件里，寻找 `他说："你好"`。

精确匹配要求字符一致，因此找不到，返回“未找到匹配”。

模型为什么会困惑？因为读取工具原样返回了弯引号，模型提交的也确实是弯引号，但它不知道中间层改了参数。再次提交相同内容，仍然会经历同样的转换和失败。

### 写入时，也会发生同样的问题

```text
模型要求写入：他说：“你好”
          ↓ 中间层替换了引号
文件实际写入：他说："你好"
```

这次工具可能报告写入成功，但保存的内容已经不符合原来的要求。随后读取文件，模型就会发现：“我明明要求写弯引号，怎么变成了直引号？”

### 与我们的草稿工具有什么关系

这就是参数保真：**传递工具参数时，应保留参数所表达的实际内容。**

我们的 create_draft 可以检查正文是否全为空白；但有效正文应原样保存，不能未经约定就删除缩进、替换标点或改写文字。这也是为什么用 trim 判空，却返回并保存原字符串。

排查这类问题时，要对照三个位置：**模型传出的参数 → 工具实际收到的参数 → 文件中的实际内容**。只看模型输出，可能看不到中间层造成的变化。
