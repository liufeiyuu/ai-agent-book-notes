# 第二周复盘：上下文、用户记忆与 RAG

> 学习记录覆盖：2026-08-29 ～ 2026-09-06。“第二周”指学习计划单元，不强行对应七个自然日。
>
> 阶段收尾：2026-09-06；实现语言：TypeScript。
>
> 依据：学习对话、章节笔记、实验源码与运行 Trace。

## 阶段结论与验收边界

第二周选定的知识主干、两个最小离线实验及综合场景题已完成，可以进入下一学习阶段。已经能够解释信息从哪里来、怎样进入上下文、怎样跨会话保存、怎样检索与更新，并根据证据定位部分失败原因。

完成范围是概念复述、代码定向阅读、受控修改、指标解释与场景判断。实验代码由助手搭建，学习者完成预测、阅读、修改与复述；不据此认定已经独立实现生产系统。真实 Embedding、模型自动压缩、持久记忆写入和完整 Agentic RAG 均未在本周接入验证。

还有一项记录需要保留：系统提示词组织框架已经讲解，但第二章前测中的“部分通过”没有完整的独立编写复测证据。下一次编写业务 Prompt 时补验，不把它改写成全部熟练掌握。

## 学习原则：抓大放小

优先掌握组件边界、完整数据流、关键取舍、失败诊断和证据。参数、数学推导和生产实现按项目需求取回。

实验是否值得做，按能否回答具体学习问题判断。教学模拟的价值在于让过程可观察、可修改；其结果能支持多强的结论，应由实现方式与测试范围决定。

本周采用的有效方式：先预测 → 读关键函数 → 改一个变量 → 看 Trace 和指标 → 解释变化 → 恢复基线。实践不能只交付代码和结果表，还需要明确学习者应观察什么。

## 一张知识框架

| 组件或信息 | 回答的问题 | 本周形成的边界 |
| --- | --- | --- |
| 原始轨迹 Trajectory | 发生过什么？ | 用户、模型和工具交互的事件记录；运行时压缩不等于永久删除原始记录 |
| 上下文 Context | 模型本轮需要看什么？ | Harness 从历史、记忆、知识库及业务状态等来源选择和组织的工作集 |
| 用户长期记忆 | 跨会话需要记住什么？ | 用户相关事实、偏好和事件，按需读取并按证据更新 |
| 知识库 | 有哪些可引用的外部知识？ | 保存领域知识及来源、版本、适用条件；可见范围仍受权限约束 |
| 业务状态 | 订单等业务对象实际怎样？ | 以业务系统为准；用户记忆提供线索，不能代替权威查询 |
| RAG | 怎样找到证据并用于回答？ | 检索、选择证据、注入上下文、生成；检索与生成分别评测 |
| Model | 根据现有信息下一步做什么？ | 提出检索、澄清、行动或回答 |
| Harness | 怎样执行并控制循环？ | 构造上下文、调度工具、记录结果、执行权限和终止限制 |

这些组件在一个任务中相互连接：相关历史、记忆、业务查询和知识检索结果进入 Context；Model 据此决策；Harness 执行并带回观察，开始下一轮。

## 已建立的知识重点

### 1. 上下文工程

- 上下文与完整历史不是固定的超集关系：可以省略旧历史，也可以加入历史之外的信息。
- 对话历史包含 User、Assistant/Tool Call、Tool Result；工具定义描述可用能力，不是一次调用的实际参数。
- 工具结果通过调用 ID 与先前 Tool Call 配对。保留因果关联，不能只凭位置猜测。
- 系统提示词组织可参考 Role、Goal、Workflow、Constraints、Tool Policy、Output Format、Stop/Escalation。
- Tool 提供可执行能力；Skill 提供按需加载的方法与流程。索引和详细内容不必都常驻上下文。
- 稳定前缀有利于缓存复用，动态信息尽量后置；新增 token 仍要计算，规则确有变化时可以更新前缀。
- 状态栏保留当前目标、TODO、关键约束、已完成动作和失败记录。它是有损表示，不自动覆盖原始轨迹中的所有重要事实。
- 上下文既可能装不下，也可能装得下却难以利用。压缩应同时考虑信息价值、窗口预算及缓存重建代价。

压缩分级：硬约束保持明确、精确标识符原样保留、任务状态结构化、失败动作与原因及重试决定一起保留、大型原文保留必要事实与可回溯来源、无关闲聊可移出运行时上下文。

### 2. 用户记忆

- 写入：从交互提取候选，核对来源、长期价值、时间、冲突和保存范围，再新增、更新、删除或不操作。`ADD / UPDATE / DELETE / NOOP` 是一种决策框架，不是所有实现必须采用的物理存储方式。
- 读取：按当前任务找相关信息，只注入当前步骤必要的部分。存进记忆库并不意味着每轮全部加载。
- 稳定偏好、临时请求、历史事件、精确标识符需区别处理；格式选择取决于关联、更新和查询需求，不机械绑定某种卡片格式。
- 状态变化保留有效历史；用户纠错时，错误旧记录不应继续作为真实历史参与检索。
- 明确时间与来源，不把未知生效时间凭空补成确定日期。身份、时间与适用范围有助于消除看似矛盾的记录。
- 会员号等精确字段适合精确查询；语义偏好可按语义召回。相关信息也不必把完整敏感字段都暴露给模型。

### 3. RAG 与分阶段评测

离线准备文档、分块、关联元数据并建索引；在线根据问题检索候选，按需要融合和重排，选择证据进入上下文，再生成回答。混合检索与重排是可选组件，不是 RAG 的定义要求。

- 块过大可能混杂主题并带入噪声；块过小可能丢失指代、条件和完整证据。
- 稀疏检索依赖词项匹配；稠密检索利用表示的语义相似性。两路原始分数尺度不同，不能未经处理直接相加。
- 融合形成统一候选，重排重新评价候选；已被上游排除的文档不能靠下游重排凭空恢复。
- Recall@K 检查相关证据覆盖；MRR 检查第一条相关结果的位置；时效与业务适用性需要额外检查。
- 本实验每个查询只有一个正确文档，因此 Recall@K 等同于该文档的命中检查；多相关文档时，还需考虑找回了多少相关文档。
- 诊断按初始候选、融合、重排、最终上下文、生成与引用逐层追踪。最终“排第 8”本身不足以确定根因。

### 4. 知识更新与 Agentic RAG

- 发布时间不等于生效时间。按问题对应的时间和业务条件选择版本，历史查询可以使用旧版本。
- 原始证据、整理后的知识、服务索引是不同层。原文更新后，还需同步受影响的分块、索引和相关缓存。
- 增量更新吸收新证据；定期整理核查重复、冲突与摘要偏差，并回查原始来源。
- Agentic RAG 将检索作为工具，由模型根据观察决定后续查询、澄清或回答。固定执行多次检索仍可以只是工作流。
- 没到次数上限不代表必须继续搜。继续搜索需要有望补齐缺口的新方向；缺用户信息时先澄清。
- Harness 执行次数、时间、费用等限制。达到终止条件后说明已知信息和缺口，不能把“停止搜索”当作“问题已解决”。

## 实验一：上下文压缩

固定输入和验收规则，对比三种表示。基线结果来自[实验报告](../experiments/context-compression-minimal/README.md)与[TypeScript Trace](../experiments/context-compression-minimal/runs/latest-typescript.json)。

| 策略 | 字符数 | 压缩后 / 原始 | 信息保留 | 体积下降 |
| --- | ---: | ---: | --- | --- |
| 不压缩 | 20,226 | 100.0% | 通过 | 未通过 |
| 滑动窗口 | 346 | 1.7% | 未通过 | 通过 |
| 任务感知结构化压缩 | 1,019 | 5.0% | 通过 | 通过 |

亲手修改的观察：删除 `failedAttempts` 后，比例从 5.0% 下降到 4.4%，但失败路径检查失败，测试从 4/4 变为 3/4。恢复后四个测试通过。

收获：压得更小不等于压得更好，体积必须与关键信息保留联合验收。

边界：结构化状态由代码写死；字符串检查只能证明预设信息仍在，不能证明自动提取稳定、模型理解正确或行动遵守约束。字符数除以 4 只是粗略估计，不是真实 Token 计费结果。

## 实验二：RAG 检索与重排

固定六份文档、三个查询与 Top-2。基线结果来自[实验报告](../experiments/rag-retrieval-minimal/README.md)与[TypeScript Trace](../experiments/rag-retrieval-minimal/runs/latest-typescript.json)。

| 策略 | Recall@2 | MRR | 时效检查 |
| --- | ---: | ---: | --- |
| 稀疏检索 | 66.7% | 0.611 | 未通过 |
| 语义代理检索 | 66.7% | 0.556 | 未通过 |
| 混合检索与规则重排 | 100.0% | 1.000 | 通过 |

### 两次受控修改

| 修改 | 实际观察 | 能支持的结论 |
| --- | --- | --- |
| Top-K 从 2 改为 3 | 稀疏检索 Recall 从 66.7% 到 100%；MRR 和正确文档位置不变 | 扩大选取范围可以提高覆盖，但没有改善评分和排序 |
| 恢复 Top-2，仅从求和中移除 `freshnessBoost` | C 的退款查询中新旧政策交换位置；Recall 不变，时效检查失败 | 当前时效加权影响版本排序，未改变正确政策是否进入 Top-2 |

学习者对第一项的观察：

> Recall变了呀，之前是66.7%，现在是100%。MRR没变，正确文档的位置没变。

学习者对第二项的观察：

> recallAtK 没变，freshness 变了

恢复后，学习者确认五个测试全部通过并结束实验。整理复盘时发现保存的 Trace 仍是消融结果；2026-09-06 在已恢复的源码上重新运行 demo，编译通过，并刷新为上表基线。测试通过记录来自此前验证与学习者恢复确认，本次文档整理未重复执行测试。

### 必须保留的限制

- `semanticConcepts` 是人工标签，未调用真实 Embedding。HTTP-403 标签不一致是人为注入的失败，不是真实模型的测量结论。
- 0 分文档按 ID 打破平局；正确登录文档因扩容进入 Top-3，不证明系统识别了其语义。
- C 同时使用 RRF、标识符奖励、语义奖励和时效加权。不能把 C 的全部收益都归给融合，也不能据此宣称混合检索普遍最好。
- 当前实现给整个小语料库排序，没有模拟大型索引的候选截断；Trace 记录两路排名及评分信号，但不是完整生产管线的所有阶段快照。
- 无真实生成器，未测试最终答案、引用忠实度、实际延迟与费用。时效检查也只是新旧版本的相对位置，不是完整业务资格判断。

## 综合场景验收

题目：“上次买的那个耳机，拆封了还能退吗？”详见[完整题目、原始回答与反馈](./03-memory-and-knowledge/refund-rag-integration-review.md)。

最终修正：

> 两个耳机订单都查出来以后，应该让用户澄清他需要的是哪个耳机的订单信息。
>
> 因为这个排第一的知识文档并不一定适用于这个业务场景。

验收通过：能够区分目标歧义与检索问题；根据订单事实检查政策范围、时间、条件及来源；证据不足时选择补查、澄清或说明无法确认。
