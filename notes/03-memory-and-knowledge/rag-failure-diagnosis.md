# RAG 故障定位与分阶段 Trace

> 核心原则：先确认失败发生在哪个阶段，再判断根因；不能仅凭最终排名直接归因。

## 诊断顺序

```text
最终答案错误
└── 正确文档是否进入初始候选？
    ├── 否：召回问题
    └── 是
        └── 是否进入融合后的候选池？
            ├── 否：融合问题
            └── 是
                └── 是否进入重排序后的最终 Top-K？
                    ├── 否：重排或 Top-K 截断问题
                    └── 是
                        └── 模型是否依据证据正确回答？
                            ├── 否：生成、提示或证据使用问题
                            └── 是：本次 RAG 链路通过
```

## “正确文档排第 8”能说明什么？

可以确定：如果系统只注入 Top-5，那么正确证据没有进入最终上下文，`Recall@5` 检查失败。

不能确定：仅凭“第 8”无法判断是哪一个组件造成的，因为 RAG 流程中存在多份排名。

| “第 8”所在阶段 | 初步归因 |
| --- | --- |
| 初始检索排名 | 初始召回或检索排序问题 |
| 稠密、稀疏结果融合后的排名 | 融合策略问题 |
| 重排序前第 4、重排序后第 8 | 有证据归因于重排序 |
| 只知道最终排名第 8 | 只能确认最终排序不理想，不能定位根因 |

因此，排名是一种症状；阶段间的排名变化才是定位证据。

## 原文已更新，为什么回答仍使用旧条款？

“原文已更新”还需要确认改的是哪一层，再沿着数据流逐层排查：

| 已确认的更新位置 | 下一步检查 |
| --- | --- |
| 原始公告（原始证据层）已更新 | 整理后的知识是否吸收了新内容，包括生效时间和适用条件 |
| 知识文件（知识层）已经正确 | 受影响的分块、检索索引和缓存是否同步更新 |
| 检索结果已经正确 | 最终传给模型的上下文是否包含正确条款，以及模型是否正确使用证据 |

不能把“原始证据更新”“知识文件更新”“检索结果更新”和“回答正确”当成同一件事。每一层都需要检查实际内容及版本，才能定位旧信息停留在哪个环节。

## 最小 Trace

每条查询至少记录：

```text
query
gold_document_ids
sparse_ranking
dense_ranking
fused_ranking
reranker_input
reranker_output
final_top_k
generated_answer
cited_document_ids
```

示例：

```text
正确文档：policy_2026
稀疏排名：3
稠密排名：12
融合排名：4
重排前：4
重排后：8
最终 Top-5：未进入
```

在这个例子中，正确文档由第 4 名降至第 8 名，才有充分证据把这次退化归因于重排序阶段。

## 评测边界

- `Recall@K` 说明正确证据是否进入前 K 个结果，不直接说明为什么没有进入。
- 正确证据进入上下文，不代表模型一定会理解、引用或遵守它。
- 最终答案碰巧正确，也不代表答案来自检索证据；还需检查引用与证据忠实度。
