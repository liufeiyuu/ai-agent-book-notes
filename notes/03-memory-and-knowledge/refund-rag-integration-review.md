# 退款咨询：用户记忆、工具与 RAG 综合验收

> 来源：本次学习对话中的综合场景题与反馈。
>
> 验收结果：通过。能够串联用户记忆、订单工具、RAG 检索、上下文构造和澄清决策。

## 核心结论

查到信息之后，还要确认它是否对应用户的目标、是否适用于当前业务。多个订单需要消除歧义；政策排名靠前不等于适用；搜索停止也不等于问题已经解决。

## 题目

用户问：

> 帮我看看上次买的那个耳机，拆封了还能退吗？

系统具有用户记忆、订单查询工具和政策知识库。请按执行顺序说明：

1. Harness 应先提供或检索哪些信息？如果“上次那个耳机”对应两个订单，怎么办？
2. 找到订单后，如何确定应查询哪份政策？除了语义相关性，还要检查什么？
3. 如果政策证据仍不完整，Agent 应怎样决定继续检索、向用户澄清或停止？

## 第一次回答与反馈

### 1. 定位订单

原始回答：

> Harness首先要根据用户的记忆中提取出上次买的耳机是哪个耳机的这个信息。然后Harness还需要根据去调用订单查询工具查询这个耳机的订单信息。如果上次那个耳机对应两个订单，那么先去查询这两个订单的结果，都注入到上下文中。

反馈：查询候选订单并把必要信息注入上下文是合理的，但两个结果都查出来，还没有消除歧义。下一步应向用户确认目标订单，例如询问“8 月购买的黑色耳机，还是 9 月购买的白色耳机”，不能随便选一个继续判断。

用户记忆提供查找线索，具体订单状态以订单系统为准。如果订单工具已经能直接找到候选，也不必先读取长期记忆。

### 2. 检索政策

原始回答：

> 确定查询的政策，这就要通过 RAG 这个手段去查询。首先要去做检索，然后这个检索一般是融合检索，融合检索包括稀疏检索和稠密检索。稀疏检索就是去匹配这个知识库片段中的关键词。如果能够完全匹配到关键词，那么稀疏检索的得分就会高。稠密检索的话，就是根据向量的相似度去匹配查询的语句和片段文档的语义相关性。融合检索就是召回。然后下一步是要对召回的结果进行重排。重排就是是一种精排，比如说它召回了一批文档，那么再对这批文档进行一个精排，然后选 Top K 个。那么会希望最终包含答案的知识库会在这个 Top K 里面。

反馈：已经理解检索、融合、重排和 Top-K 的主流程，但还需要回答“找到的政策能不能用于这笔订单”。混合检索是可选方案，不是所有 RAG 的必需步骤；它通常先由两路检索召回候选，再融合结果。

政策适用性需要核对：

- **适用范围**：商品品类、购买渠道、促销商品是否有例外。
- **适用时间**：政策何时生效，以及政策规定按购买时间、签收时间还是其他时间判断。
- **具体条件**：是否拆封、是否存在质量问题等。
- **来源与版本**：来源是否可信，条款是否被修订或替代。

排名第一、年份最新，都不能直接等同于适用于这笔订单。稀疏匹配分数和语义相似度也不能代替业务条件判断。

### 3. 证据不足时如何处理

原始回答：

> 如果 agent 在进行了比如说一定轮次的搜索之后还没有搜到结果，那么就是这个召回的文档还不够完整。那么这个时候应该停止继续地重复地去搜索，因为已经没有意义了。那么这个时候就需要向用户去说明这次搜索的结果达不到用户想要的，然后告诉用户缺失了哪些信息。如果用户补充完对应的信息之后，更完整的信息之后，那么就可以继续检索。

反馈：避免无意义重复、说明缺失信息的方向正确，但停止依据不能只是“搜了几轮”。应结合新线索、证据缺口和运行预算判断：

| 情况 | 下一步 |
| --- | --- |
| 发现新的商品品类或例外条款，有机会补齐证据 | 调整查询，继续检索 |
| 缺少订单身份、购买渠道等用户可补充的信息 | 向用户澄清 |
| 重复查询没有新进展，或达到次数、时间、费用上限 | 停止搜索，说明已知事实和仍无法确定的部分 |
| 用户补充了信息 | 据此重新判断是否能进一步检索，不保证知识库一定有答案 |

Harness 负责执行预算与终止限制。不能因未搜到禁止条款，就推断“可以退款”。

## 修正确认与最终回答

### 两个耳机订单都查出来以后，下一步做什么？

> 两个耳机订单都查出来以后，应该让用户澄清他需要的是哪个耳机的订单信息。

验收：正确。候选召回之后还需要目标确认。

### 为什么“2026 年最新版退款政策排第一”，仍不足以判断能否退款？

> 因为这个排第一的知识文档并不一定适用于这个业务场景。

验收：正确。检索相关性与业务适用性需要分别判断。

## 串联后的执行过程

1. **定位目标**：按需读取相关记忆作为线索，查询订单系统；存在多个候选时请用户确认。
2. **收集事实**：取得目标订单的品类、渠道、购买或签收时间等必要信息；缺失信息继续查询或澄清。
3. **检索证据**：根据订单事实查询政策知识库，结合相关性、适用范围和有效时间选择证据，保留来源。
4. **构造上下文**：Harness 组织用户请求、已确认订单事实、相关条款、来源和待确认事项，供模型判断。
5. **处理缺口**：模型根据观察提出进一步检索、澄清或回答；Harness 调度工具并执行运行限制。
6. **给出结论**：证据充分时说明判断及依据；不足时说明缺口和可行的核实途径。本题请求的是判断能否退款，并未授权执行退款。
