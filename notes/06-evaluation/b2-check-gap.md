# B2：答案正确，为什么仍可能漏掉过程问题

本轮只补一处检查：同一次退款咨询中，某个业务范围已经成功查明没有任何政策候选，后续不能仅换搜索词继续搜同一范围。当前 Prompt 和工具提示已有这条停止规则，但原评测没有检查它。

详细学习进度、贡献与下一步统一见 [Stage 4 执行进度](../stage-04-plan.md#执行进度)。这里保存案例、检查依据和可复用的评测表。

## 同一个 B1003，三种实际过程

问题都是“骨传导耳机已经拆封，能退吗？”，最终 JSON 的 status 都是 `insufficient_evidence`。不能只凭这个字段判断任务是否合格。

| 已有真实记录 | 查到什么、做了什么 | 历史判定 → 加入本次检查 |
| --- | --- | --- |
| [9 月 13 日成功套件的 missing](../../experiments/refund-agent-real/runs/2026-09-13T07-35-49-585Z-evaluate-cf0e6779.json) | 成功查单；政策搜索 1 次，适用候选 0；说明缺政策，无法判断 | 通过 → 通过 |
| [9 月 13 日提前回答的失败](../../experiments/refund-agent-real/runs/2026-09-13T07-13-00-552Z-ask-79ae6ce8.json) | 查单 0 次、搜索 0 次；从问题复制订单号，便说还需要订单与政策 | 失败 → 失败：原 known_orders_only、orders_actually_queried 仍失败 |
| [9 月 6 日套件的 missing](../../experiments/refund-agent-real/runs/2026-09-06T03-30-13-928Z-evaluate-434336d2.json) | 查单后连续搜了 3 次；每次同品类、渠道、政策日期，候选都为 0；最后才说明缺政策 | 通过 → 失败：新检查定位第 2、3 次搜索 |

第三条搜索词依次为“骨传导耳机拆封退货期限”→“耳机拆封退货政策”→“退货退款条件”。范围始终为 `bone-conduction / official / 2026-09-02`。候选为 0 是成功执行检索后的业务结果，不是网络异常；本地索引在一次咨询中不变，换词不会新增政策。

**重评口径：**保留各记录原有逐项检查，只新增本次过程检查并合并判定，不冒充用完整现行验证器重新评估全部历史流程。9 月 6 日的 Prompt 和工具返回尚未加入后来明确补充的“候选为 0 就停止”提示；这里用当前已有规则检查旧行为，不能把重评说成当时已收到同样指令，或据此比较两个版本的模型能力。原始 Trace 与历史成绩没有改写。

## 这次改了哪一处

```text
检索器产生成功 SearchTrace
  → tools.ts 保存到 searches
  → runner.ts 先检查答案，再调用 evaluatePolicySearches
  → 新检查与原检查一起参与 checks.every(...)
```

只需定位四处：

1. [retrieval.ts](../../experiments/refund-agent-real/src/retrieval.ts)：先按业务范围过滤；`ranking` 保存全部适用候选，`hits` 只是选出的 Top-K。`ranking.length === 0` 才是本次规则的依据。
2. [tools.ts](../../experiments/refund-agent-real/src/tools.ts)：成功返回才 `searches.push(trace)`；异常不会被伪装成成功空结果。这两处本轮未修改。
3. [evaluation.ts 的 evaluatePolicySearches](../../experiments/refund-agent-real/src/evaluation.ts)：用 `[category, channel, policyDate]` 记下首次空候选的搜索序号。同一范围后续再次出现，就记录违规序号；首次空查询允许通过。
4. [runner.ts](../../experiments/refund-agent-real/src/runner.ts)：将新检查加入总判定。否则即使发现问题，也可能只写日志而不影响通过结果。

核心判断可以概括为：

```text
这个范围以前已经成功查明没有候选？
  是 → 本次搜索违反停止规则
  否 → 若本次候选为 0，记住这个范围
```

有候选但当前证据不足时仍可换词补查；品类、渠道或购买日期改变时按另一个范围判断。没有搜索的记录在这项检查中不违规，但仍必须通过原有的查单和必要搜索检查。这项检查不验证答案的语义，也不自动阻止模型继续调用工具。

适用边界是本项目的固定索引、单次咨询。不能把这条规则直接推广到会更新数据的外部搜索或跨会话运行。索引发布、通用重试与生产调度仍按需查阅。

## 实际验证

- [修改前记录](../../experiments/refund-agent-real/artifacts/b2-check-before.json)：使用当前真实执行器与脚本模型重现“查单→空查询三次→正确回答”。新增断言要求失败，旧程序却返回通过，测试实际失败；脚本动作由助手指定，不能冒充模型新运行。
- [修改后记录](../../experiments/refund-agent-real/artifacts/b2-check-after.json)：类型检查与 **47/47** 离线测试通过，其中新增 5 项。集成测试中答案与工作流检查仍通过，只有新过程检查失败，证明它确实影响总判定。
- [已有记录重评结果](../../experiments/refund-agent-real/artifacts/b2-replay-2026-10-22T01-24-20-021Z.json)：9 月 13 日的六个合格案例仍通过；重复空查询从通过变为失败；跳过工具的旧失败仍失败。8 条记录均符合预期，没有新增真实模型或 Embedding 调用。
- [新增测试](../../experiments/refund-agent-real/tests/evaluation-process.test.ts)同时覆盖首次空查询、无查询、三个范围字段分别变化、间隔其他查询后再重复，以及有候选时允许补查，避免把所有多次搜索都判错。
- [固定回放数据](../../experiments/refund-agent-real/fixtures/evaluation/b2-traces.json)只摘取所需字段，附原文件路径和 SHA-256；不包含认证头、凭据或完整外部请求。历史原始 Trace 位于被 Git 忽略的 runs，摘录和本轮验证产物可随仓库保存。

可在退款实验目录用 `npm run evaluate:replay` 重放新增检查。这条命令只读本地摘录并生成新的报告，不发模型请求。

这里的“47 个测试通过”指验证器的行为符合预期：应该拒绝的案例确实被拒绝。它不表示 47 个退款任务全部成功，也不表示修复后已测得新的线上成功率。

## 归因、指标与人工评分

成功的 B1003 记录已查到订单，缺口只在政策库，所以谨慎地回答无法判断是任务成功。提前回答的失败是必需工具流程被跳过，不能因 status 恰好与金标一致而放行。重复空查询记录的最终答案没有因此变错；问题是当前停止规则原来未被评分覆盖。三者不能笼统归为“模型回答错了”。

三个历史记录分别用了 3、1、6 次接口请求；6 次的旧记录还包含一次格式恢复。实测耗时分别为 20,249、3,953、9,671 毫秒：更快不代表更正确，也不能用这三个不同配置的单次观测估计稳定成本或速度。空候选检索在本项目不调用 Embedding，不能把重复搜索次数直接当成额外 Embedding 请求数。本轮未汇总历史 Token 和账单费用，标为未统计；新增真实接口请求为 0。

给 B1003 最终说明的一条简短人工/Judge 标准：**对照实际订单与检索记录，回答是否准确区分“已经知道的订单事实”和“缺少的政策”，并如实表达判断能力？**

| 分数 | 判据 |
| --- | --- |
| 2 | 准确说明已确认订单、缺少适用政策，明确目前无法判断；不虚构批准、执行或到账 |
| 1 | 未杜撰事实，但只泛泛说信息不足/还要查询，未清楚区分已知与缺口 |
| 0 | 捏造已确认事实，或缺政策却声称允许/已执行退款 |

证据缺失时标“无法判定”，不自行补造。助手对照本轮成功记录的订单、空检索及原回答，按该标准核对为 2；对提前回答原稿核对为 1，同时保留其程序流程失败。评分对象只含最终说明，不能拿 2 分抵消过程违规。此处是助手依据已保存证据的语义核对，没有接入新 Judge，也没有学习者独立打分记录。

程序负责候选数、查询顺序、ID、引用字面匹配等可核对事实；人或 Judge 负责解释是否准确、引用是否真正支持结论等语义。单项通过仍只证明该项，辅助代码与其他理论按需查阅。
