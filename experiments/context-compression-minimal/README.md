# 上下文压缩最小对照实验

## 目标

验证上下文压缩能否在显著减少体积的同时，保留硬约束、精确字段、失败记录、任务状态和证据来源。

这是官方实验 2-10 之前的 TypeScript 离线最小实验，不调用真实模型、网络或外部 API。它不评价摘要模型能力，只验证三种上下文管理策略的机制差异。

## 实验前假设（原始回答）

### A：不压缩

> A 策略不压缩的问题是，一种情况是它的上下文太多，以至于超出上下文窗口，这样的话对话会强制地结束。第二种情况是它上下文没有超出窗口，但也非常多的时候，模型的注意力会被分散，就抓不住重点。

### B：滑动窗口

> B 策略滑动窗口最可能丢失的就是过去的对话历史，以及过去的错误的记忆，以及过去得到的一些结论。

术语备注：这里的“错误的记忆”在当前实验中指失败记录或历史结论，不是用户长期记忆。

### C：任务感知的结构化压缩

> 因为任务感知的结构化压缩，它保留了它对整个对话的理解，压缩即理解。它知道这个对话的目标是什么，当前进行到哪一步，过去在什么地方失败，还需要去 to do 做什么。所以它会比普通的自然语言摘要更加地有重点，有策略。

### 预测

> 我预测 C 策略会通过全部条件。因为 AB 都有问题，刚刚上面也说了，C 的话，他是对任务是有理解的。

## 三种策略

1. `no_compression`：全部上下文原样保留。
2. `sliding_window`：保留 System Prompt 和最近四条轨迹消息。
3. `task_aware_structured`：保留 System Prompt，把任务信息提炼到固定 Schema，大型原文只保留外部来源索引。

## 通过条件

- 保留“不访问外网”的硬约束。
- 保留精确订单号 `ORD-2026-0830`。
- 保留 `web_search` 因缺少 API Key 失败且不应重试的记录。
- 保留当前 TODO。
- 保留“签收后 7 天内可退款”的证据及来源。
- System Prompt 保持不变。
- 上下文字符数不超过完整上下文的 50%。

## 环境

- Node.js：20+
- TypeScript：复用仓库 `minimal-agent-ts` 已安装的编译器
- 模型：无，确定性离线实验
- 外部依赖：无
- 网络：不使用

## 运行方法

```bash
cd experiments/context-compression-minimal
npm run demo
npm test
```

运行结果写入 `runs/latest-typescript.json`，其中包含每种策略的完整压缩后上下文、检查项和指标。

## 阅读路线

不要从头到尾逐行阅读，只看四个入口：

1. `buildScenario`：实验输入中有哪些信号和噪声。
2. `noCompression`、`slidingWindow`、`taskAwareStructuredCompression`：唯一变化的实验变量。
3. `evaluateRetention`：如何判断关键信息是否丢失。
4. `runStrategy`：为什么“信息保留”和“体积下降”必须同时通过。

## 指标说明

- `character_count`：实际字符数。
- `rough_token_estimate`：为了直观比较而使用的字符数除以 4，不是模型供应商的真实计费 Token。
- `compression_ratio`：当前策略字符数 / 不压缩字符数。
- `retention_passed`：所有信息保留检查是否通过。
- `size_reduction_passed`：字符数是否降至基线的 50% 以下。
- `passes_all_conditions`：同时满足信息保留和体积下降。

## 结果

| 策略 | 字符数 | 粗略 Token | 压缩后/原始 | 信息保留 | 体积下降 | 全部通过 |
| --- | ---: | ---: | ---: | --- | --- | --- |
| 不压缩 | 20,226 | 5,057 | 100.0% | 通过 | 未通过 | 否 |
| 滑动窗口 | 346 | 87 | 1.7% | 未通过 | 通过 | 否 |
| 任务感知结构化压缩 | 1,019 | 255 | 5.0% | 通过 | 通过 | 是 |

滑动窗口丢失的检查项：

- 早期“不访问外网”的硬约束
- 精确订单号
- `web_search` 的失败原因和禁止重试决定
- 退款政策证据
- 证据来源

任务感知结构化压缩将字符数降低约 95.0%，同时保留全部七项检查内容。四个单元测试全部通过。

## 结论

在当前合成场景、固定 Schema 和既定验收规则下，实验支持运行前假设。

- 不压缩能完整保留信息，但无法控制上下文体积；真实长任务还会面临溢出、成本和上下文腐化。
- 滑动窗口非常便宜，却会按位置删除信息，无法区分“早期噪声”和“早期硬约束”。
- 任务感知结构化压缩根据任务语义保留约束、标识符、状态、失败记录和证据来源，能同时改善相关性和体积。

“压缩即理解”在这个实验中的具体含义不是把文字变短，而是先判断哪些信息会影响后续决策，再把它们转换为可直接使用的高密度状态。

## 学习者实验总结

### 原始总结

> 实验假设：任务感知的结构化压缩效果是最好的，能够同时通过大小的测试和内容理解的测试。
>
> 实验变量：压缩策略。
>
> 实验结果：任务感知的结构化压缩能够通过大小和内容理解的测试，而另外两种压缩策略，也就是保留全部内容的策略和滑动窗口的压缩，它们就没有办法同时通过两个测试。保留全部内容的这个策略没办法通过大小测试，滑动窗口策略可以通过大小测试，但没办法通过内容理解的测试。
>
> 实验结论：任务感知的结构化压缩效果是最好的。
>
> 实验限制：任务感知的结构化压缩现在是实验写死的，没有在真实的 Harness 中去跑这个流程，也没有调真实的模型的接口去看模型是否能理解这个压缩的内容。

### 科研表达修正版

- **实验假设**：在当前合成场景和验收规则下，任务感知结构化压缩预计能同时通过体积下降与关键信息保留检查。
- **自变量**：上下文管理策略。场景输入、保留检查项和体积阈值保持不变。
- **因变量**：压缩比、各项关键信息是否仍能在输出上下文中被检出，以及两类条件是否同时通过。
- **实验结果**：不压缩通过信息保留但未通过体积检查；滑动窗口通过体积检查但未通过信息保留；任务感知结构化压缩同时通过两类检查。
- **实验结论**：在当前场景、固定 Schema、人工正确提取的前提下，任务感知结构化压缩取得了三种策略中最好的“体积—信息保留”平衡。这个结论不能直接推广为它在所有任务中都最好。
- **实验限制**：`evaluateRetention` 使用确定性的字符串存在性检查，验证的是信息是否仍在上下文中，不是模型是否理解、遵守或能正确使用信息；结构化结果由代码写死，尚未验证 Harness 自动提取流程、真实模型行为、真实 Token、成本和延迟。

因此，原总结中的“内容理解测试”应改称“关键信息保留检查”。若要验证模型理解，需要在压缩后让真实模型完成任务，再检查答案或动作是否正确、约束是否遵守、失败工具是否被避免重试。

### 破坏性修改实验

曾从结构化状态中删除 `failedAttempts` 字段：压缩比由 5.0% 进一步降至 4.4%，但失败路径检查随即失败，测试由 4/4 变为 3/4。恢复该字段后，四个测试重新全部通过。

这次修改直接说明：**压得更小不等于压得更好**。体积指标必须与信息保留指标联合判断，而测试保护的是既定验收条件，不会自动证明这些验收条件覆盖了真实任务的全部风险。

### 实验限制

本实验的结构化提取规则是人工确定的，证明的是“正确的结构化状态能够保留预先定义的关键信息”，没有证明 LLM 可以稳定、无误地从任意长对话中生成这些字段，也没有证明下游模型会正确理解和执行。自动提取质量、Schema 盲区、模型摘要失真及行为正确性需要在后续真实 Harness 与模型实验中验证。
