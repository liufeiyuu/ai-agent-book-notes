## 第一站：先看一次固定 RAG，不展开 Agent Loop

只打开 `src/runner.ts`，找到 `runConsultation` 中 `if (options.mode === "rag")` 这段。

这段不是让你记语法，而是看四种东西的转换：

1. `visibleOrders(...)` 拿到业务事实，不是让模型猜订单。
2. `retrieve(...)` 根据订单范围检索政策，返回 `search.hits`。
3. `buildContext(...)` 把问题、订单、证据整理成 messages。
4. `model.generate(...)` 把这些 messages 交给真实模型。

先不要跳进每个函数。看清它们的输入/输出，回答三个问题：

1. `retrieve` 得到的结果，保存在哪个变量里，之后传给谁？请指出具体代码。
2. `model.generate` 有没有接收整个知识库？你从哪一行判断？
3. 如果删掉 `buildContext` 的检索证据，仅保留问题和订单，模型还可能答对吗？即使答对，能证明什么、不能证明什么？

过关标准：能用自己的话串起来“查询事实 → 取得证据 → 构建请求 → 模型生成”。这次不要求你读完 provider、缓存或循环实现。

## 第二站：跑一次真实请求，逐字段对照

第一轮可以先读历史已验收的 `runs/2026-09-06T03-36-37-249Z-evaluate-b7c3ff4a.json` 的 normal 案例，不必立即花费 API 调用。它能说明当次请求的工作过程，不保证本次复现结果。需要亲自复现时再确认 `.env`，执行 `npm run index`（有效缓存不重复调用），然后 `npm run ask -- --case normal --mode rag`。不使用测试替身生成“成功”结果。

先读政策原文和 H1001 订单，写下预测。然后在输出 Trace 中只看：

1. `searches[0].scope`：版本选择依据来自哪里？
2. `searches[0].hits`：证据块 ID、原文、名次是什么？
3. `requests[0].messages`：这些证据确实出现在真实 API 请求里吗？
4. `rawAnswer` 和 `evaluation.checks`：模型怎样使用证据，哪项通过/失败？

回答 Trace 中以上字段位于 `cases[0]` 下。不要先看巨大向量数组，也不要只报“全部绿了”。

要交付的一句话：模型因为读到了 **哪个块的哪条条件**，结合 **哪项订单事实**，所以给出了 **什么结论**。若答错，也按这条链定位断点。

## 第三站：弄清索引和检索

看 `corpus.ts` 的 `chunkDocument`、`provider.ts` 的 `embed`、`index-store.ts` 的 `buildIndex`、`retrieval.ts` 的 `retrieve`。

只抓五件事：完整条件不能在分块时消失；每块带来源/适用时间；文档和查询必须使用同一 Embedding 模型；过滤不是语义打分；Top-K 只选择结果，不会重算分数。

实践任务：同一个查询、订单和模型，分别 `--top-k 1` 与 `--top-k 3`，用 `npm run retrieve` 运行。比较排除原因、完整 ranking、最终 hits。若关键块本来就排第一，不要硬说扩大 K 改善了召回；记录“本查询没有获得额外关键证据”也是收获。

可选延伸（本阶段不要求补做）：修改一小段政策正文后，先执行 retrieve，观察旧索引被拒绝。然后重建索引再试，最后恢复改动并再次重建。重建可能产生接口费用；没有实际更新需求时，理解收尾演示的失效机制即可。不要靠删除旧版本政策解决日期选择问题。

## 第四站：回到真正的 Agent

先预测 `normal` 与 `ambiguous` 两个案例的工具调用应该有什么不同，再执行各自的 `--mode agent`。

先看 `tools.ts` 和 Stage 1 `agent.ts`：模型输出工具名称/参数 → Harness 校验与执行 → 工具结果带相应调用 ID 进入 messages → 模型下一轮决策。

去 Trace 找实际的 `query_orders`、`search_policy`、下一轮 messages。订单号出现在模型答案里，不等于工具成功返回了订单事实；说“需要查询”也不等于执行了查询。

理解这条消息链后，再看 `workflow.ts`。本次修复增加的是“程序检查能否结束”，不是让程序伪造模型的工具调用：

1. 还没有成功查单时，只提供 `query_orders`；明确查到一单后，只提供针对该订单的 `search_policy`。这两个必需阶段使用 `tool_choice: "required"`，不附最终答案的 JSON Schema，查询参数仍由模型生成。
2. `tools.ts` 只记录成功返回的查单结果，以及成功检索的订单 ID。查到订单但适用政策为空，是“已完成搜索、缺少证据”；工具报错则还没有完成搜索，两者不能混淆。
3. 取得所需查询结果后恢复 `auto` 工具选择和严格答案 Schema；模型可以回答或必要时补查。查无可访问订单、或有多个候选时可以说明缺口/澄清。模型若提前给最终文本，`final_rejected` 记录拒绝原因，循环在原有 **6 轮、150 秒**内继续；失败或耗尽上限不会进入格式恢复。

在新 Trace 的 `cases[i].workflow` 中，找 `stage`、`targetOrderId`、`candidateOrderIds`、`orderQueries[].returnedOrderIds` 和 `policyOrderIds`。再对照 `execution.trace` 的成功工具结果与 `requests` 的真实参数，解释阶段为什么改变。多个候选不能靠模型后来任意精查一单变成用户确认；不过，没有 `--order` 时首个非空候选集仍依赖模型正确查找，程序尚未解决全部自然语言消歧。不要把“通过流程检查”解释成“目标理解一定正确”。

历史 Agent Trace 为 `runs/2026-09-06T03-36-23-063Z-evaluate-93c08974.json`，其中没有后加的 `workflow` 字段；当前修复的 Trace 见 [真实运行记录](./LIVE-RUN.md)。先理解工具循环和结束检查，再看 `formatRecovery`：它仅在流程允许结束、文本格式不合规时触发一次无工具重生成，不是新一轮 Agent 搜索。恢复后还要复查流程和目标订单，不能借格式修复绕过查证，也不代表首次输出格式正确。

过关标准：能用真实 Trace 说明“这里是模型决策，那里是程序执行”，而不只复述 ReAct。
